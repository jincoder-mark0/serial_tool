# S-066 — 종료 시 DataLogger 테스트 간헐 실패 조사

- Status: TODO
- Recommended model: **하위(Sonnet) 가능** (단, 원인이 프로덕션 경합으로 판명되면 중단·보고)
- 선행: 없음
- Skills to load: task-done
- 근거: `doc/mistakes.md` #7 후속 — 이번에 테스트명이 특정됨 (2026-08-22)

## 목적 (Why) — 이름을 몰라 미뤄뒀던 간헐 실패가 특정됐다

전체 pytest를 반복 실행하면 드물게 아래 테스트가 실패한다 (상위 실측: **6회 중 1회**):

```
tests/test_shutdown_data_logger.py::TestShutdownStopsDataLogger
    ::test_shutdown_stops_data_logger_and_preserves_written_bytes
```

`doc/mistakes.md` #7은 이 현상을 "테스트명 미확인"으로 남기며 **"재발하면
`pytest -p no:randomly --tb=long -rf`로 이름을 먼저 확보하라"**고 지시했다.
이번에 확보됐으므로 조사한다.

### 왜 그냥 넘기면 안 되는가

이 테스트가 지키는 것은 **종료 시 기록 중이던 데이터가 유실되지 않는다**는 계약이다
(S-045가 만들고 S-059가 실제로 배선한 안전장치). 그 경로가 간헐적으로 깨진다면
둘 중 하나다:

- **테스트만의 문제**(타이밍 가정, 파일 flush 대기 부족 등) — 테스트를 고친다.
- **프로덕션 경합** — 실사용에서도 종료 시 데이터가 드물게 유실된다는 뜻이다.
  이쪽이면 훨씬 심각하다.

**어느 쪽인지 판정하는 것이 이 태스크의 본체다.** 재현되지 않는다고 "해결됨"으로
처리하지 마라.

## Steps

1. **재현 조건을 먼저 좁혀라.**
   - 단독 실행(`pytest tests/test_shutdown_data_logger.py`)을 여러 번 반복해 실패하는지,
     아니면 **전체 실행에서만** 실패하는지 구분한다. 이 구분이 원인을 크게 가른다
     (전체에서만 나면 다른 테스트가 남긴 전역 상태·스레드·싱글톤이 용의자다).
   - 반복 횟수와 실패 빈도를 수치로 기록한다.
2. **실패 시점의 실제 값을 확보하라.** 무엇을 기대했고 무엇이 나왔는지
   (기록된 바이트 수? 파일 내용? 예외?) — 추측하지 말고 실패 출력을 남겨라.
3. 원인을 특정한다. 종료 시퀀스는 최근에 두 번 바뀌었으니 함께 살펴라:
   - S-059: `data_logger_manager.stop_all()` + `processEvents()` 배선
   - S-062: `port_presenter.stop_pending_scan()` 추가
   - S-061: `packet_presenter.stop()` 추가
   `git log -p -- presenter/main_presenter.py tests/test_shutdown_data_logger.py`로
   이 테스트가 언제부터 흔들렸는지 확인할 수 있다.
4. **판정에 따라 갈린다.**
   - 테스트 문제면: 테스트를 고친다. **단, 계약을 약화시키지 마라** —
     `sleep`을 늘리거나 단언을 느슨하게 해서 통과시키는 것은 해결이 아니다.
     "종료 후 기록된 바이트가 보존된다"는 검증은 그대로 유지돼야 한다.
   - **프로덕션 경합이면 고치지 말고 중단·보고하라.** 종료 시 데이터 유실은
     설계 판단이 필요한 사안이라 상위가 결정한다.
5. `doc/mistakes.md` #7에 조사 결과를 이어 적는다 (해당 항목을 갱신, 새 행 추가 아님).
