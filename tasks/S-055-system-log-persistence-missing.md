# S-055 — 시스템 로그 저장이 실제로 동작하지 않음

- Status: DONE (2026-08-22 — 하위 모델 수행, 상위 리뷰 승인·커밋 완료)
- Recommended model: **상위 판단 후 하위 가능** (기능 요구 확인 필요)
- 선행: S-052 (발견 경위)
- Skills to load: task-done

## 목적 (Why) — S-052 수행 중 발견 (2026-08-22)

시스템 로그 위젯의 "저장(로깅)" 토글 버튼은 **어디에도 연결되어 있지 않았다**.
S-052 이전 시그널 `sys_logging_started(str)`의 **구독자가 저장소 전체에 0건**이었다.

즉 사용자가 시스템 로그 저장을 켜면:
- 파일 다이얼로그가 뜨고(S-052 이전에는 위젯이 직접 띄웠다),
- REC 표시가 켜지지만,
- **파일에는 아무것도 기록되지 않는다.**

S-052는 제어 흐름(누가 다이얼로그를 열고 상태를 바꾸는가)만 통일했고, 실제 영속화 배선은
요청 범위 밖이라 손대지 않고 코드 주석과 보고로 남겼다 — 올바른 범위 판단이었다.

대조: RX 데이터 로그(`DataLogWidget`)는 `data_logger_manager`를 통해 실제로 기록된다.

## 확정 결정 (2026-08-22, 상위) — **구현한다** (제거 아님)

조사 결과 `core/logger.py`가 `RotatingFileHandler`로 이미 `logs/serial_tool_YYYYMMDD.log`에
**전체 로그를 자동 기록**하고 있다(실측: 1.99MB 파일 존재). 시스템 로그 위젯은 같은 로거의
출력을 화면에 보여주는 것이다.

그래도 **토글을 제거하지 않고 구현하는 이유**:
- 자동 로그는 **전체·전 세션**이 섞인 파일이다. 토글은 "지금부터 이 작업 구간만" 별도 파일로
  뽑는 용도라 목적이 다르다(RX 로그의 REC와 같은 개념).
- 두 로그 위젯이 이미 같은 REC UI를 갖는데 한쪽만 없애면 **S-052에서 통일한 일관성이 깨진다**.
- 눌러도 아무 일이 없는 현재 상태가 가장 나쁘다.

**저장 대상**: 화면에 표시되는 라인 그대로(필터가 걸려 있으면 걸린 대로). 사용자가 보는 것과
저장되는 것이 같아야 혼란이 없다 — 이 판단을 코드 주석에 남긴다.

## Steps

1. **텍스트 로그 라이터** — `core/data_logger.py`는 bytes 기반(BIN/HEX/PCAP)이라 맞지 않는다.
   시스템 로그는 줄 단위 텍스트이므로 **간단한 텍스트 append 라이터**를 만든다.
   - 위치는 `core/`(예: `core/text_log_writer.py`). View·Presenter가 직접 파일을 쓰지 않는다.
   - 열기/쓰기/닫기, 실패 시 조용히 버리지 않고 알린다(S-039/S-045와 같은 원칙).
   - 앱 종료 시 파일이 닫히는 경로를 보장한다(`lifecycle_manager` 종료 시퀀스 확인).
2. **Presenter 배선** — `_on_sys_logging_start_requested`가 다이얼로그로 받은 경로로 라이터를
   시작하고, `_on_sys_logging_stop_requested`가 닫는다. **시스템 로그가 화면에 추가되는 지점**
   (`SystemLogEvent` 수신 경로)에서 라이터에도 같은 줄을 넘긴다.
   - 화면 갱신 경로를 먼저 읽고, 필터 적용 후 텍스트를 얻는 지점을 찾아라.
3. 테스트: 토글 ON → 로그 이벤트 발생 → 파일에 줄이 쓰이는지, 토글 OFF 후 파일이 닫히고
   더 이상 쓰이지 않는지, 앱 종료 시 닫히는지.

## 검증 방법

전체 pytest(offscreen, 기준선 317+신규) + 실제 파일 산출물 확인(임시 디렉터리) +
캡처 1회 + ruff. 캡처 후 `settings.json` 무변경 확인.
