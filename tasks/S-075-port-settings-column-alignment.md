## 목적 (Why) — 보고 두 건이 같은 원인이었다

- "포트 설정 프로토콜과 보드레이트 박스가, 프로토콜이 조금 앞에 있는 것을 좋아하지 않는다"
- "언어를 한글/영어로 전환할 때 UI 컴포넌트 위치/크기 변화가 생긴다"

라벨이 제 글자 폭을 갖고 필드가 바로 뒤에 붙는데, 행마다 첫 라벨 길이가 달라
필드 시작 x가 어긋난다. 언어를 바꾸면 라벨 길이가 통째로 달라져 같은 이유로 이동한다.

    수정 전  ko  프로토콜 콤보 x=71 / 보드레이트 콤보 x=86   (15px 어긋남)
             en  Protocol 콤보 x=67 / Baud 콤보 x=45         (22px 어긋남)
             언어 전환 시 보드레이트 콤보 86 → 45            (41px 이동)

## 수행 결과

상단 행과 하단 스택 페이지는 서로 다른 레이아웃이라 하나의 `QGridLayout`으로 묶을 수
없다. 대신 **각 행 첫 라벨의 폭을 서로 맞춰** 뒤따르는 필드의 시작 x를 일치시켰다.

    수정 후  ko  둘 다 x=86 / en  둘 다 x=85
             언어 전환 이동 41px → 1px

고정 픽셀을 박지 않고 **현재 언어의 실제 글자 폭**에서 최댓값을 구한다. 고정값은
번역이 길어지면 잘리고 짧아지면 빈 공간이 남는다(ui_guide).

**보이지 않는 페이지는 기준에서 뺐다.** 처음에는 SPI 라벨까지 포함했는데, 그것이 가장
넓어 Serial 화면에서 ko 기준 ~50px를 늘 낭비했다. 현재 페이지만 보고, 프로토콜을
바꾸면 다시 맞춘다.

## 테스트를 두 번 잘못 짰다 (기록)

1차: 콤보의 x 좌표를 비교 → **정렬 코드를 통째로 지워도 통과**했다.
2차: 위젯 생성 전에 언어를 정하도록 고침 → 여전히 통과했다.

원인은 pytest 하네스(offscreen, 테마 미적용)의 폰트 메트릭이 네이티브와 달라 x 비교가
변별력을 잃은 것이다. 같은 함수를 독립 스크립트로 부르면 어긋남이 보이는데
(ko 81 vs 98) pytest 안에서는 보이지 않았다.

3차에서 픽셀 대신 **동작**(첫 열 라벨 폭이 가장 넓은 라벨에 맞춰 같게 강제됐는가)을
검사하도록 바꿨다. 이건 폰트와 무관하게 갈린다 — 정렬을 제거하면 3건이 실패한다.
픽셀 효과는 네이티브 실측으로 확인해 수치를 테스트 docstring에 남겼다.

## 남은 것

2행 안쪽(데이터·패리티·정지·흐름)은 언어에 따라 여전히 이동한다. 모두 같은 폭으로
맞추면 ko 기준 ~150px가 더 필요해 실익보다 손해가 크다고 판단했다. 사용자가 지목한
것은 첫 열이었다.
